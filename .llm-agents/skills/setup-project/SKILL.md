# 対話的なプロジェクト設定

## 入力と成果物

「フロントエンドに React、バックエンドに FastAPI を使う」「本の貸出管理アプリを開発する」のような文章から開始する。目的と技術スタックの片方だけでもよい。

目的、採用技術、ディレクトリ構成、開発手順を整理し、必要な設定ファイルとドキュメントを実際に更新する。設定案の提示だけで終了しない。業務機能の実装、デプロイ、外部サービスの契約は別途依頼がある場合に扱う。

## 1. 現状を確認する

- `AGENTS.md` と `.llm-agents/instructions.md`、変更対象に適用される追加の指示を読む。以降のリポジトリ内パスはルートを基準とする。
- 作業中の差分、ルートの README、`.devcontainer/`、依存定義とロックファイル、既存コードの構成を確認する。既存の実装や選定済みの技術を優先する。
- ファイル名の大文字・小文字を確認する。既存の `README.md` があれば編集し、別の `readme.md` を作らない。共通指示は `.llm-agents/instructions.md` に反映し、各エージェントの入口に複製しない。

## 2. 不足する要件を対話で整理する

入力と既存ファイルから「決定済み」「確認が必要」「任意」を分ける。既に回答された事項は聞き直さず、変更に影響する未決定事項を一度に1〜3問ずつ尋ねる。専用の質問ツールがなくても通常の会話で進める。

| 入力の状態 | 確認・提案する内容 |
| --- | --- |
| 技術スタックのみ | 目的、主な利用者と機能、データ保存の必要性を確認する。指定技術を別の技術に置き換えない。 |
| 目的のみ | 最小限の機能と利用形態を確認し、適した構成を理由付きで提案する。代替案は必要な場合に1〜2案示し、選択または選定の委任を受ける。 |
| 両方が指定済み | DB、認証、実行環境など、設定を左右する未決定事項だけを確認する。 |
| 既存構成の変更 | 変更範囲と既存構成への影響を確認し、採用済みの構成を不必要に作り直さない。 |

必要に応じて、プロジェクト名、言語、パッケージ管理方法、ランタイムの互換バージョン、DB と永続化、開発ポート、テスト・整形方法を詰める。認証や外部サービスは必要な場合だけ確認し、秘密情報そのものを尋ねない。

選択肢には推奨案と理由を添える。「おまかせ」の範囲では最小限の構成を選び、採用理由を示して進める。未回答を同意として扱わず、回答に依存しない調査を先に行う。重要でない設定値は妥当な既定値を明示して進める。

## 3. 方針を整理して設定を反映する

目的、初期の対象範囲、採用技術、構成、変更予定ファイルを短く示す。未解決の選択だけを質問し、既に合意・委任された内容を再承認のために止めない。

バージョンや設定方法は既存の依存定義と利用可能な公式資料で互換性を確認する。確認できない場合は制約を明記し、「最新」などと断定しない。

| 対象 | 反映内容 |
| --- | --- |
| `.devcontainer/devcontainer.json` | 表示名、実在するサービスとワークスペース、必要な拡張機能、ポート転送、初期化手順。既存の共有スキル登録を初期化手順に残す。 |
| `.devcontainer/Dockerfile` など | 必要なランタイムと開発ツール。既存の Python・PyYAML、RTK・検索補助ツール、非 root ユーザでの利用を維持する。 |
| `.devcontainer/compose.yaml` | 必要な場合に DB などを追加し、接続先、ヘルスチェック、起動依存、永続ボリュームを整合させる。 |
| `.devcontainer/proxy/lists/whitelist.txt` など | 新しい依存取得に必要な宛先だけを追加する。拒否リストとの競合を調べ、許可リストの空欄化やプロキシ無効化で解決しない。 |
| `.llm-agents/instructions.md` | 「プロジェクト固有の情報」を実際の目的、対象範囲、技術、構成、セットアップ・検証コマンド、規約に更新する。共通手順と共有スキルへの導線を維持する。 |
| リポジトリルートの `README.md` | 必須の修正対象とする。テンプレートの説明を、開発するアプリの目的、主な機能、技術スタック、ディレクトリ構成、セットアップ・起動・検証手順に合わせて更新する。未実装の機能は予定と明記し、開発環境の詳細は `.devcontainer/README.md` にリンクする。 |
| `.devcontainer/README.md` | 前提、コンテナの作成・再構築、依存導入、接続先、環境の検証方法を実際の設定に合わせて更新する。 |
| 依存定義、`.gitignore`、`.env.example`、`.vscode/` | 必要な場合だけ更新する。環境変数は用途と開発用の値を示し、実際の秘密情報は書かない。 |

設定変更時は次を守る。

- プロジェクト名を変更する場合は、ルートの `README.md` のタイトル、`devcontainer.json` の `name`、`compose.yaml` のトップレベルの `name`、`.devcontainer/README.md` の表示名・プロジェクト名・操作手順を一緒に更新する。表示名と Compose の識別名は用途に合った表記にし、Compose の識別名には小文字英数字・ハイフン・アンダースコアを使い、先頭は小文字英数字とする。旧名を対象ファイル内で検索し、更新漏れを確認する。
- ワークスペースのパスを変更する場合は、Compose のマウント先と `workspaceFolder`、手順内のパスを同時に揃える。表示名の変更だけならパスまで変更しない。Compose のプロジェクト名を変えると既存コンテナや名前付きボリュームと別の環境になるため、既存データがある場合は影響と移行方法を整理し、元の環境を自動削除しない。
- 許可リストを変更した場合は、`.devcontainer/README.md` の許可ホスト一覧表と関連する説明も実際の設定に合わせて更新する。
- プロキシ、エージェント拡張機能、共有指示の参照関係を保持する。内部サービスを追加した場合は必要に応じて `NO_PROXY`、`no_proxy`、VS Code の除外設定を揃える。ビルド時の通信と起動後のプロキシ経由通信を区別する。
- ブラウザからの接続先とコンテナ間のサービス名を区別し、待受アドレスとポート転送を揃える。画面と API を分ける場合は開発用プロキシまたは必要な CORS 設定も扱う。
- 依存導入や初期化は再実行できるようにし、既存データを消す処理や常駐サーバの起動を `postCreateCommand` に入れない。ロックファイルは対応する管理ツールで更新し、手書きしない。
- 空のテンプレートで起動確認が必要な場合は、最小の起動用コード・依存定義の作成を今回の範囲に含めるか確認する。設定のみの場合は未実装部分と将来用コマンドを明示し、存在しないエントリポイントを初期化処理から実行しない。
- アプリ用の Python 依存と共有スキル用の `.llm-agents/requirements.txt` を分ける。共有スキルの検証コマンドも必要な条件付きで残す。

## 4. 整合性と起動を確認する

1. 差分を読み、回答した要件が設定・共通指示・README に一貫して反映されているか確認する。同じ入力で再実行しても設定や説明を重複追加しない。
2. JSON／JSONC、YAML などを形式に合った方法で検証する。Compose を変更した場合は、利用可能ならルートで `docker compose -f .devcontainer/compose.yaml config --quiet` を実行する。
3. 記載したコマンドの実行場所、参照ファイル、スクリプト、ポート、環境変数、依存バージョンを照合する。起動確認用コードを作成した場合は依存導入とビルドまたは最小の起動・疎通確認を行う。
4. 環境を利用できる場合はコンテナのビルドと開発ツールの実行を確認する。検証で既存の開発環境やデータを停止・削除しない。必要なら分離した検証環境を使い、今回作成したものだけを後片付けする。
5. リポジトリで指定された検証を実施する。Docker、ネットワーク、実行権限などの制約で実施できなかった確認は、静的確認と区別して記録する。

最後に、採用した構成、変更ファイル、検証結果、未実施の確認、ユーザが次に行う再構築・起動手順を簡潔に報告する。未実装の業務機能を完成済みと報告しない。

## 入力例と進め方

- 「React と FastAPI を使ったアプリ」: 指定技術は決定済みとして扱い、目的と保存するデータを確認する。合意した構成に必要な Node.js・Python 環境、依存管理、ポートと API 接続、ドキュメントを整える。
- 「本の貸出管理アプリ」: 本・利用者・貸出返却のどこまでを扱うか、単独利用か複数人利用かを確認する。その回答を根拠に画面・API・保存方式を提案し、選択または委任後に設定する。入力にない予約・通知・外部認証などを自動追加しない。
